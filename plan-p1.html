検討ノート／ P1 個人OAuth調査・検討用

ASSEMBLY / P1

個人のアカウントで、
ログインする案。

React＋Vite / Workers Static Assets / Supabase Auth＋Postgres＋RLS。認証とDBの連携をまとめ、アプリの参加資格を別に確認する案です。

個人アカウントを許容する場合

パスワードや復旧の多くを個人の認証サービスに委ねる代替案。会社アカウントは使いません。個人OAuthを使うこと自体は、まだ合意していません。

部品と、つながり

ログイン
Supabase Authを個人のOAuth提供元につなぐ案。提供元の選定、同意画面、渡される属性、開発・本番の戻り先は要検証です。
データ利用
ブラウザからSupabaseのAPIを使う構成でも、RLSで会員状態・所有者・公開範囲を制御。管理用キーはサーバーや安全な管理環境だけに置きます。S13
メールとの関係
メール入力が不要でも、提供元やSupabaseにメール属性が保存され得ます。「認証基盤にもメールを渡したくない」なら、この案は条件を満たすと扱いません。

利用者は、こう使う想定です

  1. 個人アカウントでログイン

    会社SSO・会社メールのアカウントを利用しないことを参加・運用ルールに明記。個人向け提供元の設定を確認します。

  2. 招待・承認を確認

    OAuth成功と参加資格を別に判定。未承認状態では共有データを返さず、個別招待の引換や運営承認で有効化します。

  3. RLSを通して記録を読む・書く

    本人の編集権限、同期への共有、体重の初期非公開をポリシーにします。

  4. 認証サービス側で復旧

    個人アカウントの復旧は提供元に依存。別アカウントへの切替は自動で同じ人とせず、本人再確認と履歴移行の手順が必要です。

うれしいところと、引き受けること

よいところ

AuthとPostgres/RLSを一緒に利用でき、独自のパスワード・パスキー実装を減らす方向。SQLで関係データを扱いやすい。

開発・運用の負担

提供元アカウントが参加条件になる。OAuth設定、RLS、失効、メール等の属性、低稼働停止、バックアップは運営側で確認が必要です。

無料で使うための条件

Supabase FreeはDB500MB、50,000 MAU、ファイル1GB、非キャッシュ５GB＋キャッシュ５GB/月。静的画面はWorkers Static Assets。標準URL利用なら独自ドメイン購入を必須にしない案です。S26 S27 S19

ここを確認しておこう

JWTはサインアウト後も期限まで使えるので、会員状態をRLS等で参照して失効を反映。Freeのバックアップと、非活動１週間の停止条件も含めて検討しよう。S15 S26 S43

初期構成は写真なしを基準にした比較。必要な費用・管理席・既存利用量は、採用時にも再確認します。サービス別の無料枠へ →

採用前に、小さく試すこと

  • 個人OAuthを参加条件にすることと、保存される属性を合意できる。会社アカウントに依存しない。
  • 提供元ごとの設定、同意、リダイレクト、スマホ・PWA、新端末で通し動作を確認。
  • 新規・未承認・失効済みをRLSで拒否し、利用者自身が会員状態を変更できない。
  • 元の個人アカウントを失った場合に、他人に履歴を渡さず復旧できる。
  • DBと画像を分けて退避・復元でき、Freeの停止を許容できる。

状態：すべて要検証。ここは試作の合格条件案で、実装済み・本番で確認済みの項目ではありません。

この案を選ぶか、相談するとき

N1の認証保守を担えず、個人アカウントと属性の扱いを許容できる場合の第一代替。招待・RLS・失効・復元まで通して採用を相談します。メール保有を避ける条件を維持するならN1/N2を検証します。
