検討ノート／ N1 パスキー調査・検討用

ASSEMBLY / N1

メールを使わず、
パスキーで入る案。

React＋Vite / Workers Static Assets＋Hono / D1 / 個別招待＋WebAuthn。メールなしの目的に近いぶん、認証の周辺を保守する責任が大きい案です。

公開用の調査・検討資料です。推奨や数値は比較のための提案で、アプリの確定事項・採用結果・実運用の記録は掲載しません。
部品と、つながり利用者は、こう使う想定ですうれしいところと、引き受けること無料で使うための条件採用前に、小さく試すことこの案を選ぶか、相談するとき
メールなしを優先検証

メールを持たない設計を優先できる候補。Workersでの実行互換性・CPU時間・紛失時の復旧が、採用前の関門です。実装・実機検証はまだです。

部品と、つながり

配信とAPI
画面はStatic Assets、APIはHono＋Workers。D1はAPIから利用し、権限確認もAPIの責任です。
認証
WebAuthnの既製ライブラリを使う候補。暗号や検証手順を一から自作しません。SimpleWebAuthnの公式実行環境はNode/Denoで、Workers互換性はこの調査では未確認。S01 S02
保存
会員ID、資格情報の公開鍵、招待のハッシュ、セッション等と記録を関連付けます。生体情報そのものをサーバーへ保存する方式ではありません。S01

利用者は、こう使う想定です

  1. 同期であることを確認して招待

    運営者が既知の相手に個別招待を渡す案。招待は推測困難・期限付き・単回利用で、同時引換にも対応します。

  2. 端末でパスキーを登録

    招待を確認してパスキーと会員を関連付け。次回から端末の認証操作でログインします。同期パスキーの利用は個人のOS／管理サービス側の条件も伴います。

  3. 共有範囲を確認して記録

    サーバーが会員状態を確認し、自分の記録だけを変更可能に。体重は初期非公開を提案。

  4. 紛失したら、別の入口から復旧

    別のパスキー・復旧コード・運営者の本人再確認を組み合わせる案。元の会員IDへ戻し、古いセッション等を失効します。

うれしいところと、引き受けること

よいところ

アプリでメールやパスワードを保有しない設計にできる。招待や失効のルールを今回の集まりに合わせやすい。

開発・運用の負担

招待・セッション・CSRF対策・レート制限・復旧・監査記録を運営側で保守。ライブラリ採用だけで認証全体が完成するわけではありません。

無料で使うための条件

Workers Freeの動的10万回/日・CPU 10ms、D1の１DB 500MB・読取500万行/日・書込10万行/日が基準。写真や課金機能は初期構成に含めない案です。S20 S24 S25

ここを確認しておこう

パスキーはRP IDとドメインの設計が大切。後からログイン用ドメインを変えると影響が出るため、試作と本番の境界を先に決めよう。S01

初期構成は写真なしを基準にした比較。必要な費用・管理席・既存利用量は、採用時にも再確認します。サービス別の無料枠へ →

採用前に、小さく試すこと

  • 採用するライブラリの固定バージョンで、登録と検証がWorkers上で動く。Node互換フラグだけで対応済みと見なさない。
  • CPU 10ms内で安定するか実測。収まらなければ実行先や費用を見直す。
  • challengeを短期・単回にし、origin・RP ID・本人の識別・必要なユーザー検証を確認する。
  • CookieのSecure/HttpOnly/SameSite等と変更操作のCSRF対策、会員失効、招待の同時引換を確認。
  • iOS Safari／Android Chrome、新端末、全認証手段の紛失、管理者不在時の復旧を実際に試す。

状態：すべて要検証。ここは試作の合格条件案で、実装済み・本番で確認済みの項目ではありません。

この案を選ぶか、相談するとき

メールをアプリで持たない条件に合うため、最初の試作に推奨。認証・復旧を保守できなければ、個人OAuthを許容できる場合のP1を第一代替に。メールなしを維持するならN2の本番成立を検証します。
