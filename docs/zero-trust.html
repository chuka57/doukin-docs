ZT-Aの管理操作では、検証済みAccessの主体と内部運営会員IDを登録済みの対応に照合する案です。メール一致だけで自動連携しません。ZT-Bで対応表を全会員へ拡張すればIdP本人と記録の結び付きも増えます。対応を持たない場合、Accessは集団への入口確認にとどまり、二つのログインが同一人物だとは保証しません。

Workers固有の注意：ctx.accessだけに頼らない

Static Assets付きWorkerでは、ctx.accessが利用者のWorkerへ渡らない制約があります。

Accessはアプリと静的ファイルを保護しますが、内部ルーターを通るため、ctx.accessの有無だけでログイン判定を実装しないでください。Service Bindingでも自動伝搬しません。公式文書を2026-11-02に確認。[Z1]

  1. Accessの対象を決める

    ZT-BはWorker全体保護を第一候補に。ホスト単位ならcustom domain・workers.dev・プレビュー・別ルートをすべて棚卸しし、不要な入口は閉じる。ZT-Aは管理画面と管理APIの両方を対象にする。

  2. Workerで証明を検査する

    保護対象APIはCf-Access-Jwt-Assertionの署名、issuer、AUD、期限を既製JWT検証実装で確認。固定したチームの公開鍵を使い、不正・欠落・検証不能なら拒否。単なるメールヘッダーやJWTのdecodeだけを信用しない。[Z5]

  3. アプリの権限を重ねる

    その後にdoukinのセッション・会員状態・所有者を確認。AccessのBypassやService Authを人間向けAPIの抜け道にしない。

  4. 期限切れを画面で扱う

    Access Cookieとdoukin Cookieは別々。APIでAccess期限切れ時の401応答を検討し、HTMLログイン画面をJSONとして処理しない。保存中の入力を失わず、再ログイン後の再送で重複を防ぐ。[Z6]

項目提案と条件
無料枠公式料金表はZero Trust Freeを50ユーザーとして案内。アプリ参加者だけでなく同じ契約の利用者も確認。Workers/D1の枠とは別で、50人想定は余裕がない。[Z2]
契約Zero Trust Freeでもセットアップ時の支払情報登録が必要と公式に案内。月額無料と支払登録不要は別条件。[Z7]
会員失効まずdoukin会員を無効化し全セッションを失効。Accessの許可条件からも除外してセッションを失効。Access側の反映をアプリの即時失効の代わりにしない。[Z6]
復旧doukinのパスキー復旧と個人IdPの復旧を別に用意。片方だけ回復しても通れないことを説明
障害・締め出しAccess／IdP障害時に保護を外して公開しない。複数の管理者が安全な復旧経路を保持し、隔離環境で手順を試す
ログ・個人情報Access／IdPの本人属性・アクセスログにも情報が残り得る。アプリDBだけの最小化で全体の匿名性は保証しない
性能JWT検証を追加したWorkerのCPUと鍵更新時の挙動を実測。Freeで必ず収まるとは扱わない
