03 / PLATFORM

何で作り、
どうリリースする？

React＋Viteと静的配信を推奨する理由、Next.js等を選ぶ条件、３人で安全に変更を届ける手順です。

公開用の調査・検討資料です。推奨や数値は比較のための提案で、アプリの確定事項・採用結果・実運用の記録は掲載しません。
今回の推奨と、その理由運用を検討するときのベストプラクティス代替案を選ぶ条件追加調査・試作の例と確認観点アプリをつくる４つの部品配信先を見くらべよう組み合わせの境目を確認しよう３人で保守するための、小さな約束

今回の推奨と、その理由

React＋TypeScript＋Viteを静的配信し、必要なAPIだけ動かす構成を推奨します。

ログイン後の記録画面が中心で、現時点ではSSRが必須ではないためです。N1ではWorkers Static Assets＋Hono＋D1にまとめて運用先を減らします。P1へ切り替えるなら画面は静的配信を保ち、認証・DBはSupabaseへ。不要な中継APIを追加しません。S19

以下は比較条件を仮定した設計・運用例です。期限・頻度・数値・役割は検討用で、確定要件や実際の担当・設定・日程を表しません。サービスの保証値とも異なり、組み合わせの実機動作は別途検証が必要です。

運用を検討するときのベストプラクティス

  1. 環境を作る：本番と検証を分ける

    DB・認証設定・秘密情報を環境ごとに分離し、プレビューはダミーデータ専用にします。N1はパスキーのRP IDと本番URLを、実会員の登録前に固定。個人の運営アカウントに必要最小限の権限を付け、主担当と代行を決めます。

  2. 変更する：PRで再現可能にする

    依存のロックファイルとDBマイグレーションを管理し、PRで型確認・ビルド・権限テストを実行する案です。検証環境で認証から記録まで通し、秘密情報はサービスの設定へ保存。本番キーや個人データをリポジトリへ入れません。

  3. リリースする：戻し方も用意する

    担当者が検証結果を示し、別の１人が確認して本番反映。DB変更前に退避し、互換性を保つ追加変更から適用します。障害時は直前の画面／APIへ戻す手順と、DBも復元する必要がある場合の手順を分けます。DBの破壊的変更はアプリだけ戻しても直りません。

代替案を選ぶ条件

現在の前提が変わったときの選び方
代替案こちらを選ぶ場合引き受ける条件
Next.js＋OpenNextSSR等が必要になった場合、またはチームの経験による利点が追加運用を上回る場合。Workers上で使う機能・依存・CPUをプレビュー検証。経験だけで互換性を仮定しない。S17
Cloudflare Pagesチームが既存のPages運用を活かせる場合。Functionsとビルド枠を別途確認。新規の第一候補はWorkers Static Assets。S18 S21 S22
Firebase Hosting＋F1Firestore／Rulesに慣れた担当者がいる場合。Sparkで使う静的配信と、Blazeが必要な機能を分ける。復元方法もセットで比較。

追加調査・試作の例と確認観点

試作・調査の例
検証環境へのPRデプロイとリリース手順を各１本試す例。N1の認証試作との接続や、３人で保守する場合のGit連携・管理権限・代行操作の条件を比較する案です。
比較のための確認観点
新規チェックアウトから同じビルドができ、プレビューが本番データへ触れないこと。別担当者がリリースとロールバックを再現でき、認証処理が実行環境の制約に収まることを確認します。

アプリをつくる４つの部品

React＋Vite案
画面をビルドして静的に配信。記録の取得はAPIや管理型DBを利用。公開検索やSSRが必須でない今回の候補です。
Next.js案
チームの経験があるなら比較対象。静的exportと、SSR／Server Actions等を動かす構成を分けて検討します。
Hono案
Workers上のAPIを整理する候補。招待・復旧・権限が自動で完成するわけではありません。

組み合わせの境目を確認しよう

Next.jsをWorkersへ

Cloudflareの公式経路はOpenNext。Nodeと同じ実行環境だとは見なさず、使う機能と互換性をプレビューで確認します。S17

認証を入れ替えるとき

ClerkのIDはアプリの会員と関連付けが必要。独自認証を入れただけでは、SupabaseのRLSが自動でその本人を認識しません。信頼するトークンの設計が要ります。

ブラウザから直接DBを使う案と、HttpOnlyセッションでサーバーを仲介する案では、トークンの持ち方とAPIの負担も変わります。管理型SDKと自動ログインの比較を見る →

３人で保守するための、小さな約束

  1. 個人アカウントで、必要な権限だけ

    開発・運営にも会社SSOや会社メールを使いません。共通ログインを避け、保守担当を複数人にする案です。管理席数や既存の無料枠消費を確認します。

  2. プレビューは、検証データへ

    本番の会員・体重を開発プレビューへつなぎません。OAuthの戻り先やパスキーのRP IDも環境ごとに確認します。

  3. サービスを選ぶ前に、小さく動かす

    ビルドが通るだけでなく、招待・権限・失効・復旧・DB復元まで通して比較。WorkersのCPUやDB読取回数は実測します。
