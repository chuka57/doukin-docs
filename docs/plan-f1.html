ASSEMBLY / F1

Firebaseにまとめて、
テキストから始める案。

React＋Vite / Firebase Hosting＋Auth＋Firestore＋Security Rules。Sparkで使う範囲を絞り、画像アップロードや動的サーバーを初期構成に含めない案です。

一体型の代替候補

管理型の機能をまとめて使える代替候補。個人アカウント等の認証を許容することが前提です。匿名認証だけで長期の履歴の復旧を完結させる案ではありません。

部品と、つながり

配信
Firebase Hostingで静的画面を配信。SSR向けのApp Hostingとは分けます。S32 S34
会員管理
小人数では、運営者が安全な管理環境で承認を反映する案。利用者自身に会員状態の変更を許可しません。自動招待・管理処理にサーバーが必要なら別途費用を検討。
データ
共有プロフィールと体重は別文書。ルールと検索条件を同時に設計し、読み方に合わせて重複した情報の整合性も管理します。S14 S42

利用者は、こう使う想定です

  1. 個人の認証手段でログイン

    使うプロバイダを比較し、会社アカウントは不要・不使用にします。ログイン方法の選定はまだ未決です。

  2. 運営者が会員を承認

    未承認者がデータを読めないRulesを用意。コンソールや安全な管理スクリプトで承認する運用を検証します。

  3. Rulesで範囲を確認して保存

    会員状態・所有者・公開範囲をRulesで確認。常時リアルタイム購読が本当に必要かは別に判断します。

  4. 復旧・退会・データ退避

    認証手段の復旧と、Firestoreデータの復元を分けて検証。標準バックアップがSparkで無料とは扱いません。

うれしいところと、引き受けること

よいところ

配信・認証・DBの管理先をまとめられる。Firestoreに慣れたチームなら、文書単位の画面づくりを進めやすい候補。

開発・運用の負担

読取回数とRulesの設計、文書間の重複更新、手動承認、課金なしのバックアップ代替を検証する必要があります。

無料で使うための条件

SparkのFirestoreは1GiB、５万読取・２万書込・２万削除/日、10GiB転送/月。Hostingは保存10GB・転送10GB/月。画像用Cloud Storage・Cloud Functions・App Hostingはこの案に含めません。S31 S32

ここを確認しておこう

Cloud Storageは2026-02-03以降Blazeが必要。標準のPITR・バックアップ・復元も課金有効化が必要です。テキスト中心でも復元手段の未解決を残したまま採用しないでね。S33 S31

初期構成は写真なしを基準にした比較。必要な費用・管理席・既存利用量は、採用時にも再確認します。サービス別の無料枠へ →

採用前に、小さく試すこと

  • 採用する個人認証手段の無料条件、スマホ、新端末、復旧が通る。
  • 会員状態を利用者が変更できず、未承認・失効済みをRulesで拒否する。
  • 記録・セット・リアクション・非公開体重を文書化し、クエリとRulesの整合を試す。
  • Rulesの参照・再接続・リアルタイム購読を含む読取量を測る。
  • 課金なしで実用的に退避・復元できるかを検証。必要なら費用条件を見直す。

状態：すべて要検証。ここは試作の合格条件案で、実装済み・本番で確認済みの項目ではありません。
