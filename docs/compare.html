Issue #3・#4資料 v0.3 · 改訂 2026-10-31
公開用の調査・検討資料です。推奨や数値は比較のための提案で、アプリの確定事項・採用結果・実運用の記録は掲載しません。
推奨する順序と、選び直す条件選び分けの早見表各案の取扱説明書をひらこうどこから絞るとよさそう？
推奨：N1を先に試し、運用負担が合わなければP1へ。

メールを持たない条件に合わせ、個別招待＋パスキーを最初の試作に推奨します。個人アカウントを許容できる場合の第一代替はP1。これは設計上の推奨で、実測結果や本番採用の決定ではありません。

推奨する順序と、選び直す条件

優先検証の候補：N1
個別招待＋パスキー／Workers＋D1。本人の氏名・連絡先との直接の結び付きを減らす条件では、優先検証できる候補です。日々は端末別セッションの保持で手間を減らす案を併せて比較します。認証・復旧の保守と、記録等からの再識別リスクは残ります。
運用負担が合わなければ：P1
個人OAuth＋Supabaseを代替の第一候補に。管理型の認証・DB・RLSを使い、独自の認証実装を減らせます。個人アカウントの利用と、認証基盤がメール等を保有し得ることへの合意が必要です。
ほかの案を選ぶ条件
N2はメールなしを維持しつつ管理型認証を使いたい場合。ただし登録・新端末・復旧と本番ドメイン費を確認してから。P2は個人メールと配信運用を許容する場合。F1はFirestoreの経験を活かせて、退避・復元方法も用意できる場合です。

選び分けの早見表

いずれも検討用の候補。仮定した用途での評価で、提供元による順位や採用結果ではありません
案認証の条件大きな判断ポイント
N1 パスキーメール不要に設計可能認証周辺と復旧を自分たちで保守できるか
N2 ユーザー名メール・電話なしの通し検証待ち新端末・管理者復旧・本番ドメイン条件
P1 個人OAuth個人アカウントを許容提供元の属性・RLS・復旧と停止条件
P2 個人メール個人メールを許容外部SMTPとドメインを含めた費用・配信
F1 Firebase個人の認証手段を許容文書設計・読取数・課金なしの復元

各案の取扱説明書をひらこう

メールなしを優先検証

N1 パスキー ↗

React＋Vite / Workers Static Assets＋Hono / D1 / 個別招待＋WebAuthn。メールなしの目的に近いぶん、認証の周辺を保守する責任が大きい案です。

メールなし成立を要検証

N2 ユーザー名 ↗

React＋Vite / Workers＋Hono / D1 / Clerk。認証の保守を減らす候補ですが、メール・電話なしの利用が最後まで通るかを確かめます。

個人アカウントを許容する場合

P1 個人OAuth ↗

React＋Vite / Workers Static Assets / Supabase Auth＋Postgres＋RLS。認証とDBの連携をまとめ、アプリの参加資格を別に確認する案です。

個人メールを許容する場合

P2 個人メール ↗

React＋Vite / Workers Static Assets / Supabase Auth＋Postgres＋RLS / 外部SMTP。メールをログインと復旧の入口にする代替案です。

一体型の代替候補

F1 Firebase ↗

React＋Vite / Firebase Hosting＋Auth＋Firestore＋Security Rules。Sparkで使う範囲を絞り、画像アップロードや動的サーバーを初期構成に含めない案です。

どこから絞るとよさそう？

  1. まずN1で招待から復旧まで試す

    メールなしの条件に合うN1を優先。Workers互換性・CPU・端末紛失と復旧を試し、認証周辺を３人で保守できるか確認します。

  2. 運営の負担も同じ表に置く

    初期実装だけでなく、端末紛失・退会・復元・上限到達時の対応を３人で続けられるか比較します。

  3. 不合格なら条件に合う代替へ進む

    保守負担が合わず個人OAuthを許容できればP1。メールなしを維持するならN2の成立条件を検証。どちらも合わなければ要件・予算を再相談し、未確認のまま本番へ進みません。

資料の配信先と、アプリの技術選定は別だよ

このHTMLをCloudflareで共有しても、doukin本体をCloudflare構成に決める意味にはなりません。資料用のログインを、全参加者のアプリ認証条件にも引き継ぎません。
