同期が筋トレを続けるための、招待制の記録・共有アプリ。自分の記録は自分だけに保存し、見せたい記録だけ同期へ共有します。毎日の利用はログイン保持で手間を減らします。

論点統合する仕様案位置づけ

02 / DOUKIN SPECIFICATION

どのサービスが、何を担当する？

実線は配信・要求・退避の方向。ブラウザからD1へ直接接続しません。同じホストの /api/* を必ずWorkerへ送り、SPAのHTMLへフォールバックさせない構成です。

具体名担当担当しないもの
Cloudflare Workers Static AssetsViteで作った静的ファイルを配信データの認可・保存
Cloudflare Workers ＋ HonoAPI、招待、パスキー検証、セッション・会員状態の検査Node.js常駐サーバーの運用
Cloudflare D1SQLite互換のSQLデータベース。永続データの正本パスキー秘密鍵・写真の保存
利用者の認証器／パスキー管理元秘密鍵の管理と署名。生体認証は端末側生体情報をdoukinに渡すこと
外部実行ジョブ＋暗号化保管先DB export・成功監視・復元用保管製品・契約の選定は残る

画面と機能の範囲

画面できること表示・挙動の提案
記録入力実施日、種目、重量、回数、セットの保存保存前に「本人のみ」を表示。共有は別操作
自分の履歴20件単位の取得、編集・削除通信失敗時は保存完了と表示しない。再送時の重複を防ぐ
同期の記録承認済み会員の共有記録を読む共有解除後の新規取得を拒否。既に見た内容は回収できない

設定・端末パスキー追加、端末別ログアウト、全端末失効重要変更は新しいパスキー認証を要求

体重をMVPに含めるかは元資料でも別途相談項目です。本仕様案では「実装する場合も本人のみ」として設計します。リアクション、ランキング、キャラクター、オフライン編集は初期の必須範囲に追加しません。

04 / DOUKIN SPECIFICATION

招待・ログイン・復旧

場面処理・保存先失敗時
招待ランダムな招待秘密のハッシュをD1へ。連絡先は転記しない期限切れ・使用済み・同時引換は拒否
登録／ログインSimpleWebAuthnでchallenge・origin・RP ID・署名・本人確認を検証失敗理由を漏らしすぎず試行を制限
登録の確定招待消費と会員／公開鍵の作成を一体として扱う競合で複数アカウントを作らない。D1の条件付き更新とbatchを試験
普段の再訪Cookie → D1のセッション → 会員状態 → データ認可期限切れはログインへ。同じ会員IDへ戻す
全端末紛失予備パスキーか単回復旧コードで元の会員へなければ既知の本人を確認し運営者2人で承認
復旧完了古い資格情報・全セッションを失効。新しい資格情報を登録本人確認の証拠も失った場合は復旧を保証できない

期限・承認人数は元資料の提案値。認証の暗号処理を自作しません。運営復旧は仮名性と本人確認のトレードオフを伴い、連絡先名簿を新たにDBへ作らない運用にします。

05 / DOUKIN SPECIFICATION

ログイン保持は「端末ごとの入場証」

項目統合仕様案
Cookie__Host- 接頭辞、Secure、HttpOnly、Path=/、Domainなし、SameSite=Lax。HTTPS限定
サーバー側保存トークンのハッシュ、会員ID、端末識別用ID、作成・最終利用・絶対期限・失効日時
保持期限無操作7日／絶対30日を試す。自動更新で絶対期限は延長しない
共有端末永続保持を選ばない。ブラウザ終了だけに頼らずサーバー期限も有効
更新要求Origin検証とCSRF対策。GETでデータを変更しない
保管しない場所localStorageやURLにセッション秘密を置かない。Cookieや復旧コードをログへ出さない
キャッシュ認証APIはno-store。PWAや共有CDNに非公開レスポンスを永続保存しない

7日・30日は既存の追加調査から統合した設計値で、安全性の保証ではありません。追加端末にCookieをコピーせず、新しいセッションを発行します。

誰が、どのデータを扱える？

主体本人の記録他人の共有記録他人の非公開／体重招待・失効
有効な会員読む・作る・変更・削除読むのみ不可不可
運営役割を持つ会員同上読むのみ通常APIでは不可役割の範囲内
未ログイン／未承認不可不可不可不可
失効した会員（旧Cookieあり）不可不可不可不可
基盤管理者保守上のDBアクセスが可能同左技術的にアクセス可能基盤権限による

すべてのAPIで会員状態、所有者、共有範囲を確認します。所有者IDはセッション由来とし、入力値を信用しません。D1にSupabaseのRLSがある前提を置かず、SQLの条件にも所有者・公開範囲を含めます。失効反映後に開始する要求は拒否し、管理者も内容を読めないE2E暗号化とは説明しません。

07 / DOUKIN SPECIFICATION

Cloudflare D1に持つデータ

体重はこの記録・セットの系列に含めず、会員へ直接紐付く別テーブルに保存します。すべてCloudflare D1内の論理テーブル案です。

テーブル案関係／主な列守る条件
membersid、専用表示名、status、roleランダムID。利用者自身による承認・昇格は禁止
credentialsmembers 1:N、credential_id、public_key、counter秘密鍵・指紋・顔画像は保存しない
sessionsmembers 1:N、token_hash、各期限、revoked_at端末ごとの失効。会員状態を毎回確認
invites / challenges / recovery_codeshashまたはchallenge、期限、使用状態短命・単回。競合時の一回性を保証
workouts → setsmembers 1:N workouts、workouts 1:N sets記録の削除でセットが残らない整合性
weight_entriesmembers 1:N、日付、体重本人のみ。共有用クエリに混ぜない
audit_events / deletion_ledger操作主体、対象ID、日時、結果秘密・記録本文を含めない。削除／失効台帳は復元対象と別に保持

索引案：workouts(member_id, performed_at, id)、共有一覧用(visibility, performed_at, id)、sets(workout_id)、sessions(token_hash UNIQUE)。20件のカーソル取得でも走査が20行とは限らないため、rows_readを実測します。

08 / DOUKIN SPECIFICATION

Workersで使える技術・注意が必要な技術

追加調査：2026-11-01（日本時間）。公式資料による対応状況と、doukinの組合せでの動作確認は別です。ビルド時のNode.jsと、本番のWorkersランタイムを区別します。

技術動かす場所／判定仕様案への反映・根拠
React＋TypeScript＋Vite画面はブラウザ。Viteは開発・CI静的出力をWorkers Static Assetsへ。[W1]
HonoWorkers向け公式手順ありAPIの第一候補を維持。[W2]
SimpleWebAuthn server現行READMEでWorkersを対応環境に記載第一候補に具体化。ただし版固定・認証器・CPUの実測は未実施。[W3]
D1 bindingWorkerからenv.DB経由でSQLD1 prepared statementsを基本案に。ORMは初期必須にしない。[W4]
Node.js npmパッケージ一部APIは対応、一部は部分対応やstubimport成功だけで実行可能と判断しない。推移依存も確認。[W5]
nodejs_compatcompatibility_dateで挙動が変わる公式文書では2026-08-04以後はNode互換が既定有効。旧日付ではフラグ設定を確認。[W6]
fs／ローカルSQLite仮想ファイルシステムと永続ディスクは別node:fsを一律非対応とは扱わない。永続データはD1へ。[W7]
ネイティブaddon／子プロセス依存通常のWorkersにそのまま持ち込む設計は避けるbetter-sqlite3、外部バイナリ実行等を前提にしない。代替と実行経路を調べる。[W5]
Next.js＋OpenNext代替の構成SSR要件が出たときに再比較。現案では不要な互換性確認を増やさない

開発はCloudflare Vite pluginでWorkersランタイムに近づけます。lockfileとcompatibility_dateを固定し、更新PRで実ランタイムの認証・D1・エラー系を確認します。対応表は導入済み・実測済みを意味しません。
