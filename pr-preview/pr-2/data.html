04 / DATA

どこへ保存し、
どう復元する？

SQLとテキスト中心を推奨する理由、写真を追加する条件、毎日の退避と復元・削除の運用案です。

Issue #4・関連 #2 / #3確認 2026-10-30 · JST
今回の推奨と、その理由運用のベストプラクティス代替案を選ぶ条件次の作業と、運用開始の条件３つの保存先を見くらべよう写真を入れると、ここが増えるよ戻せるところまでが、バックアップ小さく運用するための約束

今回の推奨と、その理由

初期はSQL＋テキスト記録に絞り、写真アップロードは後から追加する案を推奨します。

会員・記録・セットの関係をSQLで表せ、画像の保存・配信・削除という追加運用を抑えられるためです。N1ならD1、P1ならPostgres＋RLSを選び、DBだけを別案と混ぜません。写真がMVPに必須なら、この案をIssue #2で見直します。

以下はdoukin向けの設計・運用提案です。期限・頻度・数値は合意するための初期案で、サービスの保証値ではありません。状態：未採用・実機未検証。

運用のベストプラクティス

  1. スキーマ：所有者と公開範囲を明示する

    会員、記録、セット、体重を分離。記録は内部会員ID・実施日時・公開範囲を持ち、体重は所有者だけのテーブルへ。所有者＋日時など取得条件に合わせた索引と、20件単位のカーソル取得を初期案にします。集計の全件走査を避け、実測で索引を調整します。

  2. 退避：毎日取得し、成功を確認する

    許容損失は最大24時間分（RPO）、復旧は１日以内（RTO）を目標案に。DBを毎日エクスポートして日次７世代を、運営者２人が復号できる暗号化した別の保管先に保持します。保管先の権限・費用・自動実行方法を開始前に決め、担当が毎日最終成功時刻を確認。失敗時は再取得し、24時間以上取得できなければ新規書込を止めるか目標を見直します。GitやIssueを退避先にしません。S63 S43

  3. 復元：月１回、手順を交代して試す

    本番へ上書きせず隔離した検証先に復元し、件数・会員との対応・権限を照合。復旧時は書込を停止し、別に保管した削除・失効の記録を再適用、旧セッションを無効化してから再開します。削除した記録や退会者の権限を復活させません。画像追加後は画像本体の退避も必要です。

代替案を選ぶ条件

現在の前提が変わったときの選び方
代替案こちらを選ぶ場合引き受ける条件
Supabase Postgres＋RLSP1／P2を選ぶ、またはPostgresの経験・機能が必要な場合。Freeでは定期dumpと別保管先を用意。DBバックアップは画像本体を含まない。S43
Firestore＋RulesF1を選び、文書モデルと読取量の設計を担える場合。SQLのJOIN前提を外す。Sparkでの退避・復元方法が未解決なら開始しない。S31
画像を最初から扱う写真が継続支援に必須とMVPで決まった場合。１枚0.5MB・１人１枚/日等の制限案と保持期間を決定。非公開配信、削除、画像の復元、課金契約まで含めて再見積もり。

次の作業と、運用開始の条件

次に作るもの
データ担当がダミーの記録・セット・体重でマイグレーションと索引を作成。毎日の退避先・実行方法・主担当／代行を決め、削除・失効の再適用まで含む復元手順をIssue #4でレビューします。
運用開始の条件
別担当者が退避データと手順から１日以内に復元でき、直近24時間以内の退避に戻れること。削除・失効を再適用しても権限が守られ、無料の容量・読書き枠を実測で確認できること。

写真を入れると、ここが増えるよ

保存する量

30人が毎日0.5MBの写真を１枚で、月0.45GB増加。３か月保持すると1.35GB。圧縮後のサイズと保持期間を決めよう。

見てもらう量

当月の写真を１枚あたり全体で10回配信すると4.5GB/月。過去の写真の再閲覧はさらに別です。

画像サービスの「無料」にも条件があります

R2は無料利用量付きの従量課金サブスクリプション。Firebase StorageはBlazeの課金設定が必要。Supabase Storageの1GB枠も、転送やバックアップ先とは別に考えよう。S35 S36 S33 S26

画像追加時は、最大サイズ・許可する形式・アップロード回数・非公開の配信経路を決める提案です。位置情報など不要な付加情報も残さない方針を検討します。

無料プランでも「何を、どこまで戻せるか」を確認
候補公式の機能・制約運用の提案
D1 FreeTime Travelは７日。外部退避とは別。S25変更前に復元点を確認。アカウント喪失にも備えるなら別の保管先を検討。
Supabase FreeCLI等の定期エクスポートを推奨。DBバックアップに画像本体は含まれない。S43DBと画像を別々に退避。検証環境で両方の復元を試す。
Firestore SparkPITR・標準バックアップ・復元に無料枠なし。S31課金なしで使うなら、代替の退避・復元方法と読取費用の影響を検証。

D1は実行中のエクスポートが他のDB要求を止めます。利用の少ない時間帯に実施し、所要時間を試作で測る運用案です。FTS等の仮想テーブルを含むDBはエクスポート非対応なので、追加時は退避方法も見直します。S63

小さく運用するための約束

  1. なくしてよい時間を決める

    最後の保存から何時間分の記録を失っても許容するか、何時間で戻すか。必要な頻度・保持日数・復元担当を決めます。

  2. 削除したデータを、戻しっぱなしにしない

    退会時の記録・画像・認証情報・関連リアクションを整理。バックアップの保持期限と、復元後に再削除する手順も残します。

  3. 取得は少しずつ、測って調整する

    カーソルでページ分割し、必要な項目だけを取得。所有者・日付などのインデックスを用意し、全件取得や不要な常時購読を避ける案です。

D1とFirestoreで、数え方が違うところ

D1は返した行数ではなく、クエリが走査した行数が大切。インデックス更新も書込に加わります。Firestoreは文書読取に加え、Rulesの参照・リアルタイム購読・再接続や一部クエリのインデックス読取も確認します。
