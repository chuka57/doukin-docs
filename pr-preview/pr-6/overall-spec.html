統合設計案 / 要約資料 v0.5 · 改訂 2026-11-08
公開用の調査・検討資料です。推奨や数値は比較のための提案で、アプリの確定事項・採用結果・実運用の記録は掲載しません。
1. 構成はこれだけ2. 使う人から見た仕様3. Zero Trustは、どこまで使う？4. 実装前に確認する4点
推奨案：N1 ＋ 運営・検証だけCloudflare Accessで保護。

一般会員は招待＋パスキーで参加。記録は本人のみ、選んだ記録だけ同期に共有します。運営者にはAccessの確認も追加します。以下は採用前の設計案です。

1. 構成はこれだけ

一般会員の経路：メール入力をアプリで求めず、パスキーと保持セッションで利用。

運営者の経路：個人IdP → Cloudflare Access → アプリ認証・運営役割 → 管理API。アプリの検証環境もAccessで保護し、本番とDBを分けます。

Accessは入口の確認、Honoは記録ごとの権限確認、D1は保存担当です。

2. 使う人から見た仕様

数十人規模を想定した案。体重のMVP採否と退避先は未決定です。
項目推奨する動き
参加・日々の利用個別招待＋パスキー。通常の再訪はログイン保持で入力を省く。
筋トレ記録種目・重量・回数・セットを保存。初期は本人のみ、共有は明示操作。
体重・写真体重を実装する場合は本人専用の別データ。写真アップロードは後回し。
紛失・退会予備パスキー／復旧コードで復旧。退会・失効時は会員とセッションを無効化。
情報・復元氏名・メールの対応表をアプリに持たない。日次の暗号化退避と復元試験を用意。

3. Zero Trustは、どこまで使う？

Accessを追加しても、アプリの招待・会員状態・データ権限の確認は必要です。
案保護する範囲向いている条件
推奨：運営・検証だけ管理画面・管理API・アプリ検証環境をAccessで保護一般会員の手間と本人情報の追加を抑えたい。
代替：全アプリ全会員がAccess → アプリ認証の順に通過全員の個人IdP利用と二つのログイン・復旧を許容できる。

個人GitHub等のIdPはメール等を扱い得ます。「アプリでメールを持たない」と「認証基盤にも持たない」は別です。元のN1構成はAccessなしでも比較基準として残します。

4. 実装前に確認する4点

公式確認：Workers関連2026-11-01、Access関連2026-11-02。実機・性能・本番設定は未検証。
確認点判断材料
Workers互換性Hono・パスキー・JWT検証を実ランタイムで試す。FreeのCPU 10 ms内に収まるか実測。
Accessの入口管理API・別URL・プレビューにも抜け道を作らない。Static Assetsではctx.accessに頼らずJWT検証を設計。
契約・人数Zero Trust Freeは50ユーザー枠、支払情報登録が必要。Workers/D1・ドメイン・退避費は別に確認。
復旧・期限切れスマホ2種で紛失・失効・再ログインを試す。日次退避から削除済み情報を復活させず復元できること。
必要なときだけ：構成図・技術仕様・公式出典

04 / DOUKIN SPECIFICATION

招待・ログイン・復旧

場面処理・保存先失敗時
招待ランダムな招待秘密のハッシュをD1へ。連絡先は転記しない期限切れ・使用済み・同時引換は拒否
登録／ログインSimpleWebAuthnでchallenge・origin・RP ID・署名・本人確認を検証失敗理由を漏らしすぎず試行を制限
登録の確定招待消費と会員／公開鍵の作成を一体として扱う競合で複数アカウントを作らない。D1の条件付き更新とbatchを試験
普段の再訪Cookie → D1のセッション → 会員状態 → データ認可期限切れはログインへ。同じ会員IDへ戻す
全端末紛失予備パスキーか単回復旧コードで元の会員へなければ既知の本人を確認し運営者2人で承認
復旧完了古い資格情報・全セッションを失効。新しい資格情報を登録本人確認の証拠も失った場合は復旧を保証できない

期限・承認人数は元資料の提案値。認証の暗号処理を自作しません。運営復旧は仮名性と本人確認のトレードオフを伴い、連絡先名簿を新たにDBへ作らない運用にします。

05 / DOUKIN SPECIFICATION

ログイン保持は「端末ごとの入場証」

項目統合仕様案
Cookie__Host- 接頭辞、Secure、HttpOnly、Path=/、Domainなし、SameSite=Lax。HTTPS限定
サーバー側保存トークンのハッシュ、会員ID、端末識別用ID、作成・最終利用・絶対期限・失効日時
保持期限無操作7日／絶対30日を試す。自動更新で絶対期限は延長しない
共有端末永続保持を選ばない。ブラウザ終了だけに頼らずサーバー期限も有効
更新要求Origin検証とCSRF対策。GETでデータを変更しない
保管しない場所localStorageやURLにセッション秘密を置かない。Cookieや復旧コードをログへ出さない
キャッシュ認証APIはno-store。PWAや共有CDNに非公開レスポンスを永続保存しない

7日・30日は既存の追加調査から統合した設計値で、安全性の保証ではありません。追加端末にCookieをコピーせず、新しいセッションを発行します。

07 / DOUKIN SPECIFICATION

Cloudflare D1に持つデータ

体重はこの記録・セットの系列に含めず、会員へ直接紐付く別テーブルに保存します。すべてCloudflare D1内の論理テーブル案です。

テーブル案関係／主な列守る条件
membersid、専用表示名、status、roleランダムID。利用者自身による承認・昇格は禁止
credentialsmembers 1:N、credential_id、public_key、counter秘密鍵・指紋・顔画像は保存しない
sessionsmembers 1:N、token_hash、各期限、revoked_at端末ごとの失効。会員状態を毎回確認
invites / challenges / recovery_codeshashまたはchallenge、期限、使用状態短命・単回。競合時の一回性を保証
workouts → setsmembers 1:N workouts、workouts 1:N sets記録の削除でセットが残らない整合性
weight_entriesmembers 1:N、日付、体重本人のみ。共有用クエリに混ぜない
audit_events / deletion_ledger操作主体、対象ID、日時、結果秘密・記録本文を含めない。削除／失効台帳は復元対象と別に保持

索引案：workouts(member_id, performed_at, id)、共有一覧用(visibility, performed_at, id)、sets(workout_id)、sessions(token_hash UNIQUE)。20件のカーソル取得でも走査が20行とは限らないため、rows_readを実測します。

推奨：まず運営画面・アプリの検証環境にCloudflare Accessを追加する案。

一般会員にはN1の招待＋パスキーを維持し、運営者の入口を追加で保護します。全会員に個人IdP利用を求めてもよければ、アプリ全体をAccessで囲う案も比較できます。どちらも未実装の設計提案です。

Zero Trustを、どこに入れる？

メールなしをアプリ内だけに求めるか、認証提供元にも求めるかで選択が変わります。
構成案一般会員の入口運営・検証の入口引き受ける条件
N1：現行の基準案招待＋パスキーアプリの認証・役割検査独自認証と復旧を保守
ZT-A：運営・検証だけ追加保護（推奨）N1のままCloudflare Access → パスキー → 運営役割運営者の個人IdP・Zero Trust契約を許容
ZT-B：全アプリを追加保護Cloudflare Access → 招待＋パスキー同じ入口＋運営者用の厳しいポリシー全員にIdP等を要求。二つのログイン・復旧・失効を運用

ZT-Aの管理操作では、検証済みAccessの主体と内部運営会員IDを登録済みの対応に照合する案です。メール一致だけで自動連携しません。ZT-Bで対応表を全会員へ拡張すればIdP本人と記録の結び付きも増えます。対応を持たない場合、Accessは集団への入口確認にとどまり、二つのログインが同一人物だとは保証しません。

Workers固有の注意：ctx.accessだけに頼らない

Static Assets付きWorkerでは、ctx.accessが利用者のWorkerへ渡らない制約があります。

Accessはアプリと静的ファイルを保護しますが、内部ルーターを通るため、ctx.accessの有無だけでログイン判定を実装しないでください。Service Bindingでも自動伝搬しません。公式文書を2026-11-02に確認。[Z1]

  1. Accessの対象を決める

    ZT-BはWorker全体保護を第一候補に。ホスト単位ならcustom domain・workers.dev・プレビュー・別ルートをすべて棚卸しし、不要な入口は閉じる。ZT-Aは管理画面と管理APIの両方を対象にする。

  2. Workerで証明を検査する

    保護対象APIはCf-Access-Jwt-Assertionの署名、issuer、AUD、期限を既製JWT検証実装で確認。固定したチームの公開鍵を使い、不正・欠落・検証不能なら拒否。単なるメールヘッダーやJWTのdecodeだけを信用しない。[Z5]

  3. アプリの権限を重ねる

    その後にdoukinのセッション・会員状態・所有者を確認。AccessのBypassやService Authを人間向けAPIの抜け道にしない。

  4. 期限切れを画面で扱う

    Access Cookieとdoukin Cookieは別々。APIでAccess期限切れ時の401応答を検討し、HTMLログイン画面をJSONとして処理しない。保存中の入力を失わず、再ログイン後の再送で重複を防ぐ。[Z6]
