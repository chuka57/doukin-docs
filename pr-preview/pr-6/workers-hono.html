Hono（炎）は、APIを組み立てる軽量なWebフレームワーク。

「このURLにはこの処理」「先にログインを確認」「結果をJSONで返す」を整理する道具です。Cloudflareのサービスではなく、Workers以外でも動くライブラリです。

Workersは、EC2よりLambdaに近い

EC2は仮想サーバーを借りるサービス。Workersは、リクエストなどのイベントに応じてコードを実行するサービスです。サーバー自体は存在しますが、OSや起動台数の管理をCloudflareへ任せます。AWSでの考え方はLambdaに近く、機能が一対一で同じという意味ではありません。

一般的なEC2とWorkersの比較。構成や利用プランによって運用方法は変わります。
観点Amazon EC2Cloudflare Workers
用意するもの仮想マシン、OS、アプリ実行環境Workerのコードと設定
HTTP処理自分でWebサーバーやプロセスを起動・運用HTTP要求が来るとfetchハンドラーが呼ばれる
実行環境OS上でNode.jsなどを動かせるV8ベースのWorkersランタイム。Node.js互換は部分対応
データの保存EBSなどのディスクや外部DBを設計今回の永続データはD1へ。グローバル変数をDB代わりにしない
自由度と負担自由度が高い一方、OS・更新・運用も管理基盤管理を減らせる一方、CPU・メモリ・利用APIに制約

doukinでは「保存ボタン → Workerのfetch → HonoがURLを振り分け → D1へ保存 → 応答」という流れです。SSHでWorkerへ入り、npm startを常駐させる運用はしません。サーバーを管理する手間を減らせるため候補にしています。

確認：2026-11-03。Cloudflare：Workersの仕組み ／ AWS：Lambdaの概要 ／ AWS：EC2の概要

使う言語はTypeScript。実行されるのはJavaScript。

今回の案はTypeScript（JavaScriptに型を付けた言語）で書き、ビルド後のJavaScriptをWorkersで実行します。HonoはJavaScriptでも使えます。

型は開発中の間違いを見つける助けです。外部から届くJSONの検査は、型を書くだけでは済まないため実行時にも行います。
場所書くもの実行する場所
Reactの画面.tsx：TypeScript＋JSXビルド後のJavaScriptをブラウザで実行
HonoのAPI.ts：TypeScriptビルド後のJavaScriptをCloudflare Workersで実行
D1のデータ操作SQL（文字列または.sql）Cloudflare D1が実行

まず、3つの役割を分ける

Reactはブラウザで画面を作ります。Honoは今回、サーバー側のAPIを担当します。
名前担当doukinなら
Cloudflare Workersコードを動かす実行基盤HTTP要求が来たときにAPI処理を実行
Hono処理の振り分け・共通処理・応答作成POST /api/workouts を記録作成へ振り分け
Cloudflare D1SQLデータベース会員・筋トレ記録などを永続保存

1. まずは「動いている？」と返すAPI

ブラウザから GET /api/health を呼ぶと {"ok":true} が返ります。Honoを使うと、URLの判定とJSON応答を短く書けます。

import { Hono } from 'hono'
const app = new Hono()
app.get('/api/health', (c) => c.json({ ok: true }))
export default app
比較：Honoを使わず、素のWorkersで書くと
export default {
  async fetch(request: Request) {
    const url = new URL(request.url)
    if (request.method === 'GET' && url.pathname === '/api/health') {
      return Response.json({ ok: true })
    }
    return new Response('Not Found', { status: 404 })
  },
}
別サーバーを起動してHonoへ転送する構成ではなく、Workerの中でHonoが動きます。
記述意味
app.get(パス, 処理)GET要求の担当処理を登録する。postなら作成などに使うPOST。
c（Context）その1回の要求・応答・環境設定をまとめた窓口。
c.json(値, ステータス)JSON応答を作る。200は成功、201は作成成功。
export default appWorkersが呼べるfetchハンドラーを持つアプリを渡す。

2. doukinの「保存→取得」を小さく書く

実装例は「種目名を1件保存し、自分の記録だけ取得する」ところまで。重量・セット・共有・本番認証を省いた、ローカル学習用です。

成功応答はD1の保存が終わってから返します。
要求送るもの返るもの
POST /api/workouts{"exercise":"スクワット"}201：作成したidとprivate
GET /api/workouts/:id保存時に返ったid200：自分の記録／404：なし・他人
認証なし／不正な入力トークンなし／空の種目名401／400
実装例を開く：src/index.ts（Hono＋D1）
// ローカル学習専用。招待・パスキー認証の実装ではありません。
import { Hono } from 'hono'

type Env = {
  Bindings: { DB: D1Database; DEMO_TOKEN?: string }
  Variables: { memberId: string }
}
const app = new Hono<Env>()

app.get('/api/health', (c) => c.json({ ok: true }))

// middleware：記録APIより先に共通のチェックを通す。
// DEMO_TOKENは.dev.varsだけに置く。本番には設定・公開しない。
app.use('/api/workouts/*', async (c, next) => {
  c.header('Cache-Control', 'no-store')
  if (!c.env.DEMO_TOKEN ||
      c.req.header('Authorization') !== `Bearer ${c.env.DEMO_TOKEN}`) {
    return c.json({ error: 'unauthorized' }, 401)
  }
  c.set('memberId', 'demo-member') // 学習用の固定会員
  await next()
})

app.post('/api/workouts', async (c) => {
  let input: unknown
  try { input = await c.req.json() }
  catch { return c.json({ error: 'invalid_json' }, 400) }
  if (typeof input !== 'object' || input === null ||
      !('exercise' in input) || typeof input.exercise !== 'string' ||
      input.exercise.trim().length < 1 || input.exercise.length > 80) {
    return c.json({ error: 'exercise_required_max_80' }, 400)
  }
  const id = crypto.randomUUID()
  // 所有者は送信されたmemberIdではなく、検証した文脈から取得する。
  await c.env.DB.prepare(
    'INSERT INTO workouts (id, member_id, exercise) VALUES (?, ?, ?)'
  ).bind(id, c.get('memberId'), input.exercise.trim()).run()
  return c.json({ id, visibility: 'private' }, 201)
})

app.get('/api/workouts/:id', async (c) => {
  const row = await c.env.DB.prepare(
    'SELECT id, exercise, visibility FROM workouts WHERE id = ? AND member_id = ?'
  ).bind(c.req.param('id'), c.get('memberId')).first()
  // 他人の記録の存在も応答から区別させない。
  if (!row) return c.json({ error: 'not_found' }, 404)
  return c.json(row)
})

app.onError((_error, c) => c.json({ error: 'internal_error' }, 500))
export default app
Honoが所有権や入力の妥当性を自動判定するわけではありません。実装者が条件を書きます。
注目するところ何のため？
app.use(..., next)ミドルウェア。記録処理の前に共通チェックし、通ったらnextで先へ進む。
c.env.DBWranglerでDBという名前を付けて接続したCloudflare D1。
prepare(...).bind(...)SQLの?へ値を渡す。入力をSQL文字列へ直接連結しない。
run() / first()SQL実行／最初の1行を取得。結果を待つのでawaitを使う。
c.set / c.getこの要求の中だけで、確認した会員IDを次の処理へ渡す。
WHERE id = ? AND member_id = ?IDが分かっても他人の記録を取得できないよう、SQLにも所有者条件を入れる。

3. 自分のPCで試す手順

Node.jsとnpmが必要です。生成されたプロジェクトで、下の設定とコードを使います。--localのみで試し、deployはしません。DBのゼロUUIDはローカル学習用で、本番DBのIDではありません。

手順・Wrangler設定・SQL・リクエスト例を開く
npm create hono@latest doukin-hono-demo
# テンプレートは cloudflare-workers、パッケージ管理は npm を選択
cd doukin-hono-demo
npm install
# 下の設定を反映し、表示したコードを src/index.ts に保存
npx wrangler d1 execute doukin-demo --local --file=./schema.sql
npx wrangler types
npm run dev
// wrangler.jsonc（生成済み設定へこの項目を追加・調整）
{
  "name": "doukin-hono-demo",
  "main": "src/index.ts",
  "compatibility_date": "2026-11-03",
  "d1_databases": [{
    "binding": "DB",
    "database_name": "doukin-demo",
    "database_id": "00000000-0000-0000-0000-000000000000"
  }]
}

schema.sqlとして保存：

-- ローカルのダミーデータ専用。本番用マイグレーションではありません。
CREATE TABLE IF NOT EXISTS workouts (
  id TEXT PRIMARY KEY,
  member_id TEXT NOT NULL,
  exercise TEXT NOT NULL,
  visibility TEXT NOT NULL DEFAULT 'private' CHECK (visibility = 'private')
);

.dev.varsにトークンを置き、再起動後にcurlで呼びます。Windows PowerShellではcurl.exeを使うか、同等のHTTPクライアントで送信してください。

# .dev.vars（gitへ登録しない。値は学習用）
DEMO_TOKEN="local-learning-only"

# 別のターミナルから。既定ポート8787の例
curl http://localhost:8787/api/health
curl -i -X POST http://localhost:8787/api/workouts \
  -H 'Authorization: Bearer local-learning-only' \
  -H 'Content-Type: application/json' \
  --data '{"exercise":"スクワット"}'
# 応答のidを下へ入れる
curl http://localhost:8787/api/workouts/返されたID \
  -H 'Authorization: Bearer local-learning-only'

この環境ではnpm依存を入れた実行・デプロイは未検証です。テンプレートの版により設定形式や起動コマンドが変わる場合は、生成READMEと公式手順を確認してください。

4. この例と、本番の設計案の違い

DEMO_TOKENは学習専用です。例をそのまま本番へ公開する設計ではありません。
学習用の例本番へ進むときに追加すること
固定トークン＋固定会員招待・パスキー・端末別セッションを検証し、有効な内部会員IDを設定。利用者が送るmemberIdを信用しない。
種目名だけ・本人のみ記録とセットの整合、明示共有、体重の分離、再送時の重複防止。
最低限の入力検査リクエストサイズ、試行制限、Cookie認証時のCSRF対策、ログに秘密を出さない監視。
ローカルのD1本番・検証の分離、マイグレーション、バックアップ・復元、CPUと走査行数の実測。
Access未使用運営用APIはAccess JWTとアプリの運営役割を両方検査。Hono自体はAccessの代わりにならない。
